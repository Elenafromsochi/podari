# «Подари»: диагностика и восстановление

Проверено 6 сентября 2026 года. Репозиторий: `Elenafromsochi/podari`.
Исходный `main`: `c4c57eae7533f42dcb3b7c4f745f82008c87099d`.

## Вывод

Оснований переписывать проект с нуля сейчас нет. Код и история сохранены,
сайт открывается, серверные функции создают запрос входа в Telegram, API Auth
отвечает. Полный вход заказчицы пока не воспроизведён: неизвестен её сценарий,
нет доступа к серверу и подтверждения в её Telegram.

**Рабочий сайт пока не исправлен.** Подготовлено локальное исправление одного
доказанного дефекта. Сервер, DNS, webhook и схема БД не изменялись. Во время
браузерной проверки сайт сам создавал временные nonce обычного экрана входа;
подтверждение входа, создание пользовательских аккаунтов и отправка сообщений
от имени пользователя не выполнялись.

### Последний откат не соответствует опубликованному фронтенду

В `main` коммит `c4c57ea` от 31 августа отменяет часть правок Telegram-входа:
`AuthFlow.tsx` снова выводит `https://t.me/...`. Однако свежая браузерная
загрузка показывает ссылку `tg://resolve?...`, характерную для предыдущих
правок. Получены assets `index-DiE5f7dD.js` и `index-6gOB9Dx2.js`, надпись `v134`.

Это подтверждает расхождение фронтенда с `main`, но не устанавливает точный
серверный commit. `v134` не является надёжным идентификатором: он не менялся
при нескольких исправлениях. Нужно сопоставить checkout, время сборки,
запущенный процесс и публичные assets. Причина может быть в невыкаченном коде,
старом `dist`, другом каталоге запуска или другом сервере.

### Доказанный дефект `/db`

Обработчик передавал `request.body` (ReadableStream) в Node `fetch` без
`duplex: "half"`. Локальный HTTP-тест воспроизводит исключение
`RequestInit: duplex option is required when sending a body` и HTTP 502.
Исправление добавляет этот параметр для запросов с телом, сохраняя потоковую
передачу. Обработчик вынесен из `src/server.ts` в `src/lib/supabase-proxy.ts`,
чтобы тестировать его без запуска фоновых рассылок приложения.

До исправления: 4 из 8 тестов падают. После: 8 из 8 проходят на Node 22.22.3.
Запуск: `npm run test:proxy` (Node 22.6+ с поддержкой strip-types).
Проверены методы с телом, запросы без тела, сохранение пути, query,
заголовков, ответа upstream и редиректа.
Требование описано в [документации Undici](https://github.com/nodejs/undici#requestduplex).

Дополнительная проверка: сборка `NITRO_PRESET=node-server npm run build`
успешна; ESLint нового обработчика и теста проходит; `bash -n` диагностического
скрипта проходит. Полный `tsc --noEmit` не проходит: 49 ошибок, причём
сравнение исходного `src/server.ts` и исправленного даёт идентичные диагностики
(0 различий). Это существующий долг по типам в данном окружении, не успешная
полная проверка проекта. Логи сохранены локально в `.diagnostics/`.
Зависимости установлены через npm по диапазонам `package.json`, как в текущем
deploy-скрипте; точные версии на рабочем сервере неизвестны. `bun.lock` сохранён
без изменений. Перед релизом нужно зафиксировать и проверить набор зависимостей.

**Ограничение:** текущий опубликованный JS настроен на `https://api.23podari.ru`,
а не `/db`. Исправление нужно для пути `/db`, в том числе указанного в
репозиторном `.env`, но не доказывает причину жалобы заказчицы. WebSocket
Realtime через Node `/db` этим исправлением также не проверен.

### Что ещё требует проверки, прежде чем менять вход

- Кнопка бота после подтверждения ведёт на корень сайта без nonce. Если
  Telegram откроет отдельный браузер/WebView, у него может не быть сессии
  исходной вкладки. Это конкретная гипотеза по коду, нужен сценарий на устройстве.
- Telegram-вход может перезаписывать пароль существующего пользователя
  вычисленным паролем, если вход с ним не удался. Это конфликтует с отдельно
  установленным паролем. Нельзя менять этот механизм без теста сохранения
  существующего аккаунта и его данных.
- Вход по паролю на новом устройстве всё равно требует кода через Telegram.
  Это сейчас не независимый от Telegram резервный вход.
- VK и Яндекс используют отдельные синтетические email. Вход другим способом
  может создать другой профиль: нельзя выдавать это за восстановление старого.
- `deploy/deploy.sh` пересобирает текущий каталог и не обновляет unit-файл
  systemd. Новые настройки сервиса могут не примениться от одного `git pull`.
- Старые заметки о VPN и провайдерах — история обсуждений, а не измерение
  текущей доступности. Нельзя по ним автоматически обвинять VPN пользователя.

## Порядок восстановления

1. **Инвентаризация без изменений.** На фактическом сервере проверить
   checkout, запущенный процесс, Node, Caddy, Docker, путь `dist`, тома БД и
   Storage. Подготовлен `deploy/diagnose-readonly.sh`: передать его на сервер
   отдельным файлом и выполнить `bash diagnose-readonly.sh /opt/podari`
   с поправкой на реальный каталог. Скрипт не выводит значения секретов,
   не делает SQL-запросов, не перезапускает сервисы и не меняет webhook.
   Содержимое `.env`, полные `docker inspect` и сырые журналы публично не отправлять.
2. **Резервные копии до вмешательства.** Сначала сохранить текущую работающую
   сборку и конфигурацию, затем согласованный комплект БД и файлов (ниже).
3. **Проверить реальный деплой отката.** Выяснить, почему `main` и публичная
   сборка различаются. Не запускать вслепую старые install/migrate-скрипты.
4. **Воспроизвести вход с журналами.** Согласованная попытка на реальном
   устройстве: создание nonce → `/start` в боте → получение webhook →
   подтверждение nonce → выдача сессии → загрузка исходного профиля.
   Для VK отдельно проверить разрешённый redirect и обмен кода.
5. **Изолированный стенд.** Отдельная БД, хранилище и тестовый бот; фоновые
   напоминания и рассылки отключены. Нельзя запускать копию приложения с
   рабочими ключами: `src/server.ts` сам запускает reengagement-задачу.
6. **Минимальное исправление и приёмка.** Сначала восстановить вход именно
   в прежний профиль с его подарками, чатами и балансом. Затем повторный вход,
   выход, перезагрузка и обновление сессии, фото, подарки, чат. Повторить на
   устройстве заказчицы, через Wi-Fi/мобильную сеть без VPN и при необходимости с ним.
7. **Публикация проверенной сборки.** Зафиксированный commit и зависимости,
   отдельный каталог сборки, проверка до переключения, сохранённый предыдущий
   release. Отдельно согласовать момент изменения действующего сайта.
   После переключения сверить публичные assets и выполнить реальный вход.

SQL-дамп не содержит сами файлы Storage; это прямо указано в
[документации Supabase](https://supabase.com/docs/guides/platform/backups).
Не копировать работающий каталог Postgres обычным `cp` как единственный бэкап.
Для согласованности БД и файлов при резервировании определить короткое окно
без записей либо подходящий механизм снимков после осмотра хранилища.

Предлагаемый режим после восстановления: ежедневная автоматическая копия,
отдельная копия перед релизом, хранение вне основного VPS в российском хранилище,
шифрование, ограниченный доступ, уведомление об ошибке и регулярный пробный
restore. Срок хранения согласовать, например 7 дневных и 4 недельных копии;
ежедневный режим допускает потерю изменений с последней копии.

**Уже сделано локально:** `.diagnostics/podari-before-repair-20260906.bundle`,
проверен `git bundle verify`. Это копия кода и всей доступной истории, не
копия рабочей БД, фотографий или серверных настроек.

## Схема работы без обязательного VPN

Текущая архитектура по коду уже допускает собственный VPS:

```text
Браузер → DNS/HTTPS → Caddy → Node-приложение
Браузер → api.23podari.ru → Caddy → Supabase gateway
Node → Supabase → Postgres / Auth / Storage / Realtime
Node ↔ Telegram Bot API; браузер ↔ VK ID
Node → proxyapi.ru (ИИ-функции)
Резервирование → отдельное защищённое хранилище
```

Фактическое размещение всех компонентов ещё нужно подтвердить в кабинете.
Покупать новые серверы и подключать дополнительные ИИ для починки входа
сейчас не требуется. ИИ-функции приложения не должны определять доступность
авторизации. Для входа без зависимости от Telegram сначала проверить VK;
привязку к существующим профилям проектировать отдельно и сохранять user_id.

GitHub нужен для кода, VPS — для приложения и данных, регистратор/DNS — для
адресов, отдельное хранилище — для бэкапов. Проксирование Cloudflare не является
обязательным для этой схемы; его переключение не заменяет исправление приложения.
Обещать доступность во всех российских сетях до проверки на реальных сетях нельзя.
