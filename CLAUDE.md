# Подари (23podari.ru)

Сервис для дарения подарков и исполнения желаний. TanStack Start, self-hosted на Timeweb Cloud VPS (Node.js через systemd `podari.service`, Caddy как reverse proxy + TLS), self-hosted Supabase (Postgres + Auth + Storage + Realtime) на том же сервере. Cloudflare — только DNS/CDN перед сервером (не Workers — с них переехали 2026-08).

## Важные факты (не забывать)

- **Telegram сам по себе заблокирован в России и требует VPN у пользователя** — независимо от того, доступен ли сам сайт 23podari.ru. Это ограничение приложения Telegram (MTProto-протокол), не нашей конфигурации. Если пользователь жалуется, что вход через Telegram не работает даже при включённом VPN — скорее всего у него VPN настроен только на браузер/Safari, а не на всё устройство целиком (Telegram как приложение идёт отдельным трафиком). Обсуждали 2026-08-11.

- **Деплой на сервере — как делать правильно, чтобы не ронять сайт.** Всё через веб-консоль Timeweb (пользователь на iPad, без SSH-клиента и без gh/git на своей машине):
  1. `git pull origin main` на сервере — **этого мало**, если менялся `deploy/podari.service`: systemd не подхватывает изменения файла-юнита сам по себе. Нужно ещё `cp deploy/podari.service /etc/systemd/system/podari.service && systemctl daemon-reload`.
  2. Рестарт (`systemctl restart podari`) может занимать **до ~90 секунд** — старый Node-процесс не всегда завершается по SIGTERM быстро (похоже, из-за долгоживущих WebSocket-соединений Supabase Realtime, которые сервер проксирует), и все эти секунды Caddy отдаёт 502. Смягчили через `TimeoutStopSec=10` в `podari.service` (2026-08-11) — но если однажды при рестарте сайт коротко «не грузится», это ожидаемо, не паника; надо просто подождать секунд 10-15 и проверить `systemctl is-active podari caddy` + `journalctl -u podari -n 20`, а не сразу чинить код.
  3. **Мерж PR через GitHub API после squash-мержа предыдущего PR из той же ветки часто даёт фантомный `405 merge conflicts`**, даже если реального конфликта нет (squash создаёт на main новый коммит с другим SHA, но тем же содержимым — git не считает историю идентичной). Чинится так: `git fetch origin main`, `git show <старый-коммит-ветки>:<файл> > /tmp/файл`, `git checkout -B <ветка> origin/main`, вернуть файл обратно, закоммитить, `git push --force-with-lease`, смержить снова.
  4. **Перед тем как предлагать новую правку в коде входа/деплоя — сначала проверять, что предыдущий деплой реально применился** (просить вывод `systemctl is-active` и/или `journalctl`), а не сразу писать следующий спекулятивный фикс. В этой сессии несколько раз чинили код вслепую, хотя проблема была в незавершённом деплое или во временном 502-окне при рестарте — это раздражало пользователя намного больше, чем сама причина.
  Обсуждали 2026-08-11.
